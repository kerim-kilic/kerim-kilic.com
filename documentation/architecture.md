# Architecture

A static site (Hugo) served from a private S3 bucket through CloudFront, with DNS in Cloudflare, infrastructure in
Terraform, and keyless deployments from GitHub Actions. Two environments come from one Terraform module.

## Request path

```
browser --> CloudFront --> S3 (private bucket, origin access control)
              |  viewer-request function: clean URLs (+ www redirect on prod, + secret-header check on dev)
              |  TLS with an ACM certificate (us-east-1), managed cache and security-header policies
              `- 403/404 from S3 are mapped to /404.html with status 404
```

- The bucket blocks all public access. Only the CloudFront distribution can read it, through origin access control (OAC).
- A private bucket answers a request for a missing key with 403, so CloudFront maps both 403 and 404 to the site's own
  `/404.html` and returns a real 404 status.
- The CloudFront Function (`terraform/modules/site/function.js.tftpl`) rewrites `/x/` to `/x/index.html` and `/x` to
  `/x/index.html`, because neither CloudFront nor the S3 REST endpoint maps folders to index documents.
- HTML is cached at the edge until the next deploy invalidates it and revalidated by browsers; fingerprinted CSS and
  images are cached for a year; fonts and share images for a day (see [Deployment](#deployment)).

## Environments

| | Prod | Dev |
|---|------|-----|
| Hostname | apex domain (plus `www`, redirected to the apex) | `dev.<domain>` |
| DNS | Cloudflare, DNS only (traffic goes straight to CloudFront) | Cloudflare, proxied (needed for Cloudflare Access) |
| Access | public | Cloudflare Access login, allowlisted emails only |
| Deployed from | `main` | every other branch |
| Drafts, search engines | drafts hidden, indexed | drafts shown, `noindex` and `Disallow: /` |
| Deploy role trusts | `refs/heads/main` only | `refs/heads/*`, but can only write the dev bucket |

Pull requests only build; they never deploy.

## Terraform layout

```
terraform/
  modules/site/            bucket, OAC, distribution, function, certificate + DNS records, deploy role
  modules/private-access/  Cloudflare Access application and policy, plus two zone rules (dev only)
  envs/shared/             account-wide GitHub OIDC provider (one per account)
  envs/dev/  envs/prod/    thin roots that call the modules; each has its own state key
  iam/                     policies for the person running Terraform
  state-bucket/            how the state bucket was created
```

- State lives in an S3 bucket created by hand (Terraform can't create the bucket that holds its own state), one key per
  environment, with S3-native state locking (`use_lockfile`, Terraform 1.11 or newer) and no DynamoDB table.
- Terraform runs from a workstation, not from CI. The credentials it needs are powerful (broad AWS access, a Cloudflare
  token that can edit Access and rules), Cloudflare has no OIDC federation so its token would have to be a long-lived
  secret in GitHub, and CI logs on a public repository expose account IDs and ARNs.
- Terraform code is checked in CI (`terraform fmt -check` and `terraform validate` for each stack) on every pull request
  and push. The checks need no credentials, and nothing is planned or applied there.
- Long-lived access keys are avoided: a key is created at the start of a working session and deleted at the end.

## Dev access control

Cloudflare Access sits in front of the dev hostname (Google sign-in or a one-time email code, allowlisted emails only).
The one-time code login method is created by Terraform, and the application lists its allowed login methods explicitly.
Left unset, Cloudflare also offers its own dashboard sign-in, which only members of the Cloudflare account can use.
Cloudflare then adds a secret `x-origin-verify` header to requests for that hostname, and the CloudFront Function returns
403 for any request without it. Without that check, anyone who found the raw `*.cloudfront.net` address could skip the
login. The secret is generated by Terraform and never stored in the repository.

The access module owns two Cloudflare zone rulesets (request-header transform and configuration rules; a zone has one
ruleset per phase, so hand-made rules of those types would be replaced) and sets Full (strict) TLS for the dev hostname
only, without touching the zone-wide SSL mode.

**Known difference:** dev traffic passes through Cloudflare's proxy and prod traffic does not. Browsers see Cloudflare's
certificate on dev and the ACM certificate on prod; Cloudflare can rewrite HTML (for example email obfuscation) and adds
its own cache. This was accepted, and prod is verified after go-live with `tools/smoke-test.sh`.

## Deployment

`.github/workflows/deploy.yml`: build with Hugo, then (except for pull requests) assume the environment's IAM role through
GitHub OIDC, sync to S3 in three passes with different `Cache-Control` values, and invalidate CloudFront.

- **No AWS keys in GitHub.** Each environment has its own role. The trust policy requires audience `sts.amazonaws.com` and
  a subject that names the exact repository and branch pattern. GitHub's subject claim now carries **immutable numeric
  owner and repository IDs**, `repo:<owner>@<owner_id>/<repo>@<repo_id>:ref:<ref>`, so the trust pins those IDs (they live
  in the git-ignored `terraform.tfvars`). This also stops someone who later recreates an account or repository with the
  same name from inheriting the trust.
- **Role permissions are minimal:** list, put and delete objects in its own bucket, and create an invalidation on its own
  distribution.
- **Actions stay current.** Dependabot proposes updates to the GitHub Actions the workflow uses (weekly, grouped). Its
  pull requests target `dev`, so a new version is deployed and tested there before it can reach `main`. Its own branches
  only build; they never deploy.
- **Repository variables** (not secrets) select the target: `AWS_REGION`, and `DEV_` / `PROD_` variants of the role ARN,
  bucket name and distribution ID.
- **Cache policy by file class:** fingerprinted `css/` and `images/` are `immutable` for a year; `fonts/` and `og/` for a
  day; everything else (HTML, sitemap, feeds) is revalidated by browsers and cached at the edge (`s-maxage`) until the next
  invalidation.

## Decisions

| Decision | Reasoning |
|---|---|
| Hugo | Single binary, Markdown articles, RSS, fast builds; no Node toolchain to maintain |
| Private S3 + CloudFront with OAC, not S3 website hosting | Website endpoints are HTTP-only on custom domains and need a public bucket |
| Custom theme, self-hosted fonts | No third-party dependency; avoids loading fonts from a CDN |
| One module, two environments | Test the pipeline and review content before touching the production domain |
| Cloudflare Access plus a secret header for dev | The operator's IP is dynamic, so an IP allowlist would lock them out and can't serve reviewers; per-person access and revocation; DNS is already in Cloudflare |
| Deploy roles per environment, trust defined in Terraform | A feature branch can never write to the production bucket, and the rule is enforced in AWS, not in a GitHub setting |
| `DEV_` / `PROD_` repository variables instead of GitHub Environments | Keeps the OIDC subject as `ref:refs/heads/...` so the trust conditions stay in code |
| State in S3 with native locking | No extra lock table; the bucket can be shared by other projects through per-project key prefixes |
| Test production right after go-live | Covers the dev/prod difference cheaply |

## Limits worth knowing

- A policy that can create IAM roles is effectively admin-equivalent, so the operator policy limits mistakes, not the
  impact of a stolen credential. MFA and short-lived keys are the real protection.
- Some CloudFront actions can't be scoped to a resource that doesn't exist yet, so that statement uses `Resource: "*"`.
- The operator policy was derived from the Terraform code and its action names were checked against AWS's published
  list. It has been used to apply the dev environment; tune it by adding any action an `AccessDenied` error names.
